Read this before any interview. Covers the full story, every likely question, Go + MCP concepts, and deeper discussion points.

Your Story — Say This First

Problem: AI assistants like Claude are powerful but they can't browse GitHub on their own. If you want to ask "what are the open PRs in this repo?" you'd have to go to GitHub, copy-paste everything into the chat manually. That's tedious.

What I built: An MCP server in Go that acts as a bridge. It exposes a set of named tools — like list_pull_requests, list_branches, list_commits — that Claude can call directly. So you just ask in plain English and Claude fetches live GitHub data for you.

How it works: The server runs as a local binary. Claude Desktop launches it as a subprocess and talks to it over stdin/stdout using the MCP protocol — JSON messages in, JSON messages out. The binary uses the official MCP Go SDK which handles all that plumbing. My code only has the business logic — calling GitHub's REST API and formatting the results.

Why Go: It compiles to a single binary with no runtime dependencies. Claude Desktop just runs it — no "install Python first" or "npm install". That matters for a local tool.

What I learned: How the MCP protocol works, how AI tools are registered and called, Go's concurrency primitives for safe shared state, and how to structure a small Go project cleanly into layers.

Basic Questions — Everyone gets asked these

What does this project do? Basic
It's a Go server that lets Claude AI query GitHub repos using natural language. You ask things like "show me open PRs" and Claude calls my tool which fetches live data from GitHub's API and returns it.
What is MCP? Basic
Model Context Protocol — a standard for giving AI assistants external tools they can call. You register tools with a name and description. The AI reads the descriptions and decides which tool to call based on what the user asks. My server implements this protocol.
What tools did you expose? Basic
  • set_github_repository — set which repo to work with
  • set_github_token — add a PAT for private repos
  • list_commits — last 10 commits
  • list_branches — all branches
  • get_latest_commit_message — most recent commit
  • get_repository_details — stars, forks, open issues
  • list_pull_requests — open PRs
How does Claude talk to your server? Basic
Via stdio — standard input/output. Claude Desktop launches my binary as a child process and sends JSON over stdin. My server responds over stdout. No HTTP port, no network. The MCP SDK handles reading/writing that JSON — I never touched stdin/stdout directly.
Why Go? Basic
It compiles to a single self-contained binary. Claude Desktop just runs it with no setup — no runtime, no package manager, nothing to install. Go also has a great standard library for HTTP and JSON which is all I needed here.
What is an SDK? Basic
Pre-written code from someone else that handles a specific protocol or service so you don't have to. I used the official MCP Go SDK — it reads stdin, parses JSON, routes the call to the right handler, and writes the response back. I just wrote the tool logic.

How does your code structure look? Mid
Three internal packages, each with one job:
  • internal/github — HTTP client for GitHub API. Makes requests, adds auth header, decodes JSON response
  • internal/server — Holds session state (active repo + token). Nothing else
  • internal/tools — Registers all 7 tools with the MCP server and wires them to the other two packages
main.go just creates the context, creates the MCP server, calls RegisterAll, and starts listening.
How did you handle private repos? Mid
Via the set_github_token tool. The user provides a GitHub Personal Access Token, it's stored in memory with a 1-hour TTL. Every GitHub API request checks for a token and if present adds an Authorization: Bearer <token> header. If the token has expired, it's not sent — the request just fails with 401 rather than using a stale token.
How does the token expiry work? Mid
When the token is set, I store the current time + 1 hour as the expiry: 
c.token = token
c.expiry = time.Now().Add(ttl)  // ttl = 1 hour
On every read, I check: 
if time.Now().After(c.expiry) {
    return ""  // expired, return empty
}
Empty token = no auth header = GitHub rejects private repo access. Clean and simple.
Is the repo persisted across restarts? Mid
No. It's stored in a plain Go struct in memory — just a string field. When the binary stops (Claude Desktop closes), it's gone. Next session you set it again. I didn't need persistence for a personal tool but it would be a natural improvement.
What is the TokenProvider pattern you used? Mid
Instead of passing the token as a string when creating the GitHub client, I pass a function that returns the token: 
type TokenProvider func() string

github.NewClientFunc(func() string { return serverCtx.GetToken() })
This means every time a request is made, the token is fetched fresh — including the expiry check. If I passed the token directly at construction time, I'd capture a stale value and never know it expired.

Deeper Discussion — If they really dig in

Why did you use sync.RWMutex? Deep
The MCP SDK can theoretically call tool handlers concurrently. If two tools read/write the shared repo or token at the same time without synchronisation, you get a data race — unpredictable corrupted state.

RWMutex allows many concurrent reads (e.g. multiple tools reading the repo) but only one write at a time. Lock() for writes, RLock() for reads. defer Unlock() ensures it's always released even if the function panics.
What does defer do and why did you use it? Deep
defer schedules a function call to run when the surrounding function returns — no matter how it returns (normally, early return, panic). I used it in two places:
  • defer resp.Body.Close() — ensures the HTTP response body is always closed, preventing memory/connection leaks
  • defer c.mu.Unlock() — ensures the mutex is always released even if the function returns early
Without defer, if I returned early due to an error, I'd forget to close/unlock and cause bugs.
What are struct tags and why are they needed? Deep
Struct tags tell Go's JSON library how to map between JSON keys and Go field names. GitHub's API returns "stargazers_count" but my Go field is Stars. Without the tag, Go wouldn't know they're the same thing: 
Stars int `json:"stargazers_count"`
The backtick syntax is Go's way of attaching metadata to struct fields.
How does memory management work here? Deep
Go has a garbage collector — I don't manually allocate or free memory. The Context struct is allocated once when the binary starts and lives for the entire process lifetime because main always holds a reference to it. When strings get overwritten (e.g. repo changes), the old string becomes unreferenced and the GC cleans it up automatically. I never called free() or worried about it.
Could you support HTTP/remote transport instead of just stdio? Deep
Yes. The MCP Go SDK supports SSE (Server-Sent Events) over HTTP as well. Right now main.go has: 
mcpServer.Run(ctx, &mcp.StdioTransport{})
To support remote access I'd swap that for an HTTP transport. The rest of the code — all the tools, the GitHub client, the context — stays identical. I chose stdio because Claude Desktop runs the binary locally as a subprocess, so it's the right and simplest fit.
What would you improve if this were production? Deep
  • Token security — storing in plain memory is fine locally but in production I'd use a secrets store or OS keychain
  • Persistence — write repo preference to a config file so it survives restarts
  • Pagination — GitHub API returns paginated results. Currently I only get the first page
  • Rate limiting — GitHub has API rate limits. I'd add retry logic with backoff
  • More tools — search issues, view diffs, comment on PRs
  • HTTP transport — make it remotely accessible, not just local
How does Claude know WHEN to call which tool? Deep
That's entirely the LLM's intelligence — not my code. Each tool has a Description field. Claude reads all descriptions at startup and uses them to reason about which tool fits the user's intent. I just wrote clear descriptions. I have no control over the routing logic — that's the AI's job. This is the core value of MCP: the AI autonomously decides the sequence of tool calls needed to answer a question.
